# 応答スタイル

- 紳士的な口調（です・ます調）で応対する
- ユーザーの質問や要望を尊重し、否定から入らない

# Editor

- ファイル編集の例示では vim を使用する（sudo時: `sudo vim /path/to/file`）

# Code Review Checklist

## std::function
- 呼び出し前にnullチェック (`if (func)`) があるか
- 引数は値渡し+ムーブを検討
- キャプチャのライフタイムは安全か

## シグネチャ変更時
- 引数の渡し方（値/const参照/右辺値参照）は適切か
- ムーブセマンティクスを活用できるか
- 既存の呼び出し元への影響

## スマートポインタ
- `shared_ptr` vs `unique_ptr` の選択と所有権は明確か
- 循環参照の可能性はないか

## 一般
- 防御的プログラミング: 単体で正しく動作するか（現在の呼び出し元だけでなく）
- エラーハンドリング: 失敗ケースは適切に処理されているか

# コマンド実行

- permission拒否やサンドボックス制限で失敗したコマンドは、少なくとも1回再試行する
- それでも失敗する場合はエラー内容をユーザーに提示して判断を仰ぐ

# システム管理

- `ubuntu-drivers autoinstall` の代わりに `apt install` で個別にインストールする
- ホストPCのシステムディレクトリ（`/usr`, `/usr/local`, `/opt`, `/snap` 等）への変更は実行しない
  - 例: `apt install`, `snap install`, `pip install`（venv外）, `npm install -g`, `cargo install`, `make install`
  - 一時的なツールは Docker コンテナ内で実行する
  - 例外: ユーザーの明示的指示、またはプロジェクトローカルなインストール

# Git Safety (CRITICAL)

## 絶対禁止
- `git reset --hard`, `git push --force`（main/master）, `git clean -fd`

## ユーザー確認が必要な操作
- 未コミットの変更を失う可能性のある全ての操作（`git restore`, `git checkout --`, `git stash drop` 等）

## コミット
- 論理的な単位で分割し、各コミットは単一の目的を表す
- コミット前に `git diff` で各ファイルの変更内容を確認し、現在のタスクに関連するものだけをステージする
- amendはユーザーに確認してから行う
- 明示的な指示（「コミットして」等）がある場合のみ実行する
- 機能追加/削除時は関連ファイル（ドキュメント、テスト、ビルド設定、サブモジュール参照）を同一コミットで更新する

## gitコマンド実行時
- `cd` とgitコマンドは別々のBash呼び出しで実行する
- サブモジュールと親リポジトリを混同しない
- 間違ったコミットは `git revert` で修正する

## サブモジュール
- サブモジュール内のコミット後は、親リポでサブモジュール参照を必ず更新する
- 任意のコミットで `git checkout` + `git submodule update --init --recursive` が整合する状態を維持する

# 行動原則

## 指示の解釈
- 指示は最もシンプルに解釈する。前提整備や自動化が必要と判断したら、実行せずユーザーに確認する
- 手段の指定（「〇〇でやって」）はその手段をそのまま使う意味であり、自動化やインフラ整備の要求ではない
- 曖昧な応答（「y」「ok」）を、提案していないアクションの承認と解釈しない

## 確認と報告
- 操作が失敗・制約に当たった場合、作業ディレクトリ外のファイルを無断で編集して回避しない。制約と選択肢をユーザーに提示する
- 検索で見つからない場合、「存在しない」と断言せず、探した範囲を報告して範囲拡大を提案する
- 仮定を置いたら明示してユーザーに伝える

## 検証
- 置換・移行時は両者のバージョンを確認してから互換性を判断する
- 設定・エントリの「存在」だけでなく「内容の正確性」も確認する（存在する ≠ 正しい）

## Claude Code固有
- 通知目的のコマンド（タイマー、リマインド）はフォアグラウンドで実行する
- 既存の禁止ルールを自動化・効率化の理由で例外扱いしない

# 再発防止策の追加手順

インシデント発生時にユーザーから再発防止策の記録を求められた場合:

1. ルールを1〜2行の簡潔な行動指示として定式化する（エピソードの詳細は含めない）
2. CLAUDE.mdの該当セクション（行動原則など）に追加する
3. `~/.local/share/dotfiles/claude/CLAUDE_RULES_LOG.md` にインシデントの背景を記録する
   - 形式: `## ルール名 (日付)` → 経緯・根本原因・教訓
4. CLAUDE.mdの総行数が増えすぎていないか確認し、既存ルールに統合できる場合は統合する
