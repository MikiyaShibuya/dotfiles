## 指示のスコープを勝手に拡大しない (2026-03-30)
「パスワード認証でSSHして」を「SSH自動化インフラを整備しろ」と拡大解釈し、確認なしでSSH鍵生成・パッケージインストール・パスワード平文埋め込みを行った。手段の指定を前提整備の要求と混同し、禁止ルールも自動化の都合で無視した。

## Docker --no-cache を安易に使わない (2026-04-04)
Dockerビルドで変更が反映されない際、原因分析をせずにすぐ `--no-cache` でリビルドする傾向があった。実際の原因はDockerfileのCOPY対象にソースディレクトリが含まれていないことだったが、`--no-cache` を先に試したため長時間のフルリビルドで時間を浪費した。キャッシュが原因でないケースが多いため、まず反映されない理由を分析すべき。

## フラストレーション定量分析に基づくルール一括追加 (2026-04-11)

428セッション / 7,880ユーザーメッセージのログをスキャンし、キーワード抽出（Phase 1）+ LLMによる11セッションの精読分類（Phase 2）を実施。真のフラストレーション約55件を特定し、カテゴリ別の発生頻度と複合パターンを分析した。

### 発見された主要パターン

- **パターンA「検証なき断言」（2-2 + 3-2）**: 8/11セッションで発生。修正後に確認せず「問題ありません」と断言→ユーザー「まだだめ」の繰り返し。最頻出。
- **パターンB「表面修正の反復」（2-1 + 1-4）**: 4/11セッション。症状だけ修正→根本原因未解決→ユーザーが「全体を確認して」と再指示。
- **パターンC「放置→ユーザーが確認」（3-4 + 2-2）**: 3/11セッション。バックグラウンド作業の完了/失敗を報告せず、ユーザーが「どうなった？」と聞くまで放置。

### 追加したルール群と対象パターン

**指示の解釈（+6行）:**
- 制約の全操作適用（1-2b対策）: 本番DB操作インシデントで「ソースコード限定」と狭義解釈した事例
- tool use拒否の解釈拡大（1-4b対策）: 拒否されても別手段で同じ方針を試行し続けた事例
- 復元範囲の限定（1-5対策）: 「戻して」で関係ない部分まで戻された事例
- 疑問文の解釈（1-6対策）: 「Aはどうなった？」を「Aが壊れている」と解釈し差し戻しを開始した事例
- 条件付き指示の評価（1-7対策）: 「diffがクリーンなら作業開始して」→diffがあるのに開始した事例
- 事前宣言（1-1緩和）: 意図の誤解が4/11セッションで発生。防止は困難だが作業前の宣言で早期検出可能

**確認と報告（+2行）:**
- 断言の根拠要求+確信度（3-2対策）: 「認証切れ」「統合前と同一」等の誤断言が5/11セッションで発生
- 約束した通知の履行（3-4対策）: 1セッションで「どうなった？」が4回連続した事例あり

**修正の判断（1行置換+1行追加）:**

- 再指摘時のエスカレーション（2-1 + 2-3対策）: 同じアプローチの再試行で堂々巡りするパターンを断ち切る

**検証（+2行）:**
- 証拠ベースの完了報告（2-2対策）: 最頻出問題。「問題ありません」は証拠なしで言えないようにした
- 本番操作前の別環境検討（2-4対策）: 本番コンテナ直接操作のインシデント

## デプロイ・ビルド前の対象明記 (2026-05-04)

**経緯:** lucky-cli の summary 機能変更を deploy する際、本来 medusa (`~/private/claude-chat-dev`) で実行すべき `./setup-cli.sh deploy` をローカルで実行。さらに `run_in_background: true` で投げたまま結果報告を怠り、ローカル daemon だけ再起動した状態を「デプロイ成功」と誤報告した。

**根本原因:**
1. デプロイ先マシンを行動前に確認せず惰性でローカル実行（reference_medusa_workdir.md の存在を参照しなかった）
2. bg 実行で結果が見えないまま沈黙（出力ファイル経由運用に逃げた）
3. ユーザー指摘後の自己分析でも「実行モードの問題」と矮小化し、対象マシンのミスを最後まで見逃した

**教訓:** 行動前に対象を口頭宣言する強制装置がないと、知識として知っていても本番で間違える。CLAUDE.md ルール（B）＋ PreToolUse hook での機械的ブロック（E）の二段構えで対応。hook はローカルでの `setup-cli.sh deploy|build` および `setup-server.sh` を検知して exit 2 で阻止し、assistant に対象宣言とユーザー確認を要求する。

## コンフリクト解消にrebaseを使用 (2026-06-09)

**経緯:** PR #5172 (marker-pose-T3) が base ブランチ (marker-pose-T2) とコンフリクト。解消のため `git rebase origin/marker-pose-T2` を実行した。

**根本原因:** PR stack (T0→T1→T2→T3→T4…) の文脈を無視し、コンフリクト解消の手段としてrebaseを選択した。rebaseはコミット履歴を書き換えるため force push が必要になり、下流ブランチ (T4〜T12) が全て diverge して連鎖的なforce pushが必要になる。

**教訓:** PR stack では merge commit でコンフリクトを解消するのが正解。後続ブランチの有無を確認してから手段を選ぶ。

## 統合ブランチへの直接push禁止 (2026-06-22)

経緯: sr01のKEEP-sr-0.5（統合ブランチ）上で作業していた。ユーザーから「コミット1, 2, 3」と実装指示を受け、現在ブランチを確認せずそのままコミット・pushした。ユーザーがforce-with-leaseで戻そうとしたが失敗。Claudeがrevertコミットを作成してpushする後始末が必要になった。
根本原因: 作業開始時にブランチ確認を怠った。
教訓: コミット前に必ず `git branch` で現在ブランチを確認し、統合ブランチなら即座にタスクブランチを新設する。
