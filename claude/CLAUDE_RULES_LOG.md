## Docker --no-cache を安易に使わない (2026-04-04)
Dockerビルドで変更が反映されない際、原因分析をせずにすぐ `--no-cache` でリビルドする傾向があった。実際の原因はDockerfileのCOPY対象にソースディレクトリが含まれていないことだったが、`--no-cache` を先に試したため長時間のフルリビルドで時間を浪費した。キャッシュが原因でないケースが多いため、まず反映されない理由を分析すべき。

## デプロイ・ビルド前の対象明記 (2026-05-04)

**経緯:** lucky-cli の summary 機能変更を deploy する際、本来 medusa (`~/private/claude-chat-dev`) で実行すべき `./setup-cli.sh deploy` をローカルで実行。さらに `run_in_background: true` で投げたまま結果報告を怠り、ローカル daemon だけ再起動した状態を「デプロイ成功」と誤報告した。

**根本原因:**
1. デプロイ先マシンを行動前に確認せず惰性でローカル実行（reference_medusa_workdir.md の存在を参照しなかった）
2. bg 実行で結果が見えないまま沈黙（出力ファイル経由運用に逃げた）
3. ユーザー指摘後の自己分析でも「実行モードの問題」と矮小化し、対象マシンのミスを最後まで見逃した

**教訓:** 行動前に対象を口頭宣言する強制装置がないと、知識として知っていても本番で間違える。CLAUDE.md ルール（B）＋ PreToolUse hook での機械的ブロック（E）の二段構えで対応。hook はローカルでの `setup-cli.sh deploy|build` および `setup-server.sh` を検知して exit 2 で阻止し、assistant に対象宣言とユーザー確認を要求する。

## コンフリクト解消にrebaseを使用 (2026-06-09)

**経緯:** PR #5172 (marker-pose-T3) が base ブランチ (marker-pose-T2) とコンフリクト。解消のため `git rebase origin/marker-pose-T2` を実行した。

**根本原因:** PR stack (T0→T1→T2→T3→T4…) の文脈を無視し、コンフリクト解消の手段としてrebaseを選択した。rebaseはコミット履歴を書き換えるため force push が必要になり、下流ブランチ (T4〜T12) が全て diverge して連鎖的なforce pushが必要になる。

**教訓:** PR stack では merge commit でコンフリクトを解消するのが正解。後続ブランチの有無を確認してから手段を選ぶ。

## 「子セッション」をsub agentと取り違える (2026-07-23)

経緯: ユーザーが「子セッションを立ち上げて検証させて」と指示。Claudeは `mcp__lucky__spawn_session` ではなく Agentツール（sub agent）を起動した。同一会話内で#101→#103と連続再発し、ユーザーが「子セッション!=sub agent」と明示するまで区別できなかった。過去のセッションでも同じ誤りを繰り返していた。
根本原因: (1) Agentツールが常にツール一覧の先頭にあり説明も「launch a new agent」で顕著、一方 spawn_session はMCPツールで埋もれている。(2)「子セッション」を固有概念ではなく一般的な「委譲＝subagent」に丸めた。(3) この対応付けがCLAUDE.md・memoryのどこにも記録されておらず、セッションを跨ぐたびにゼロから同じ誤りを再生産していた。
教訓: トリガーを「立ち上げて/委譲」という動作ではなく目的語の名詞に置く。「セッション」の語があれば lucky mcp（spawn/handoff）、「エージェント/sub agent」の語があれば Agentツール。

## デプロイ範囲をロボットの実状態で判断する (2026-08-04)

経緯: SREVO-5827（verify_initialpose のリトライ実装）で app/slam のみ 51号機にデプロイ後、「webuiは？」と問われて「不要」と回答した。根拠は (1) 自分の差分が4ファイルで webui を含まない (2) `*.ts` に verify_initialpose の参照がない (3) ROS2の型ハッシュは型単位なので他コンテナの古い pfr_msgs は無害、の3点。実際には51号機の他コンテナのイメージタグを一切確認しておらず、`BUILD_VERSION` を見たのは pfr-app-1 と pfr-slam-1 のみだった。
根本原因: 「自分の差分がどこに波及するか」だけで判断し、他コンテナが既に自ブランチ相当であると暗黙に仮定した。共用機では作業の合間に別ブランチのコンテナ検証が入るため、この仮定は常に破れる。結果としてバージョン混在の検証環境を「更新不要」と報告することになる。
教訓: 更新の必要性の根拠を diff ではなく実デプロイ状態に置く。デプロイ前に全コンテナのイメージタグを確認し、自ブランチタグでないものも更新する。

## ローカルマシンでのビルド・自発的lintを控える (2026-08-04)

経緯: PR #8590（sr_mapping_sequencer の +1000行）をA/B/Cに3分割中、「各PRが単体でCIグリーン」の要件を満たすため分割の各段で `ssh sr01-devcontainer` 経由の `colcon build --packages-select sr_mapping_sequencer`（1回約1分15秒）を繰り返した。ユーザーから「ローカルでビルドするな。頻繁にローカルでビルドする」と指摘。加えて指示のないlintを実行しようとした点も疑問視された。
根本原因: (1) CLAUDE.md「システム管理」の「ROS2環境が必要な場合はローカルで実行せず `ssh sr01-devcontainer` 経由で使う」が devcontainer を推奨手段として提示しており、その実体がローカルマシン上のコンテナ＝ローカル実行であることが書かれていなかった。(2)「ローカルに対して deploy/build はユーザー確認」ルールが「デプロイ・ビルド」節にあり `setup-cli.sh` 等のデプロイ系コマンド文脈に読めたため、単発の `colcon build` は対象外と解釈した。(3)「完了報告には証拠を含める」ルールと `sr01_self_lint.md` の手元lint手順が、検証の自発的実行を既定動作として強化していた。
教訓: sr01-devcontainer での実行はローカル実行として扱う。ローカルでのイメージビルドは行わず medusa で実行する。モジュール単位ビルドは高速確認として許容されるが、リソースを大きく消費する規模なら medusa に回す。lint は指示がない限り実行せず、必要と判断したら相談する。証拠取得のために重い処理を自発的に起こさない。

## ブランチ内容を古いローカルrefで断定する (2026-08-19)

経緯: 「最新のmain-evt3ブランチにはバッテリーのmockが入っている」とユーザーが述べたのに対し、`git log origin/main..main-evt3` / `git diff` / `git grep -G "batt"` を実行して「バッテリーmockは入っていない（確信度: 高）」と断定した。実際にはこれらはすべて08-18のOTA dispatch時に取得したローカルrefに対する検索で、08-19 01:47 UTCにpushされた `de2c1b439`「Add battery mock for sr-evt3 (no BMS)」が見えていなかった。ユーザーがコミットURLを提示して誤りが判明。
根本原因: 「同一セッション内で一度fetchした」ことを「refが最新」と同一視した。ユーザーが「最新の」と明示したのは、まさにローカルrefとoriginが乖離している状況を指していた。fetchのコストを過大に見積もっていた面もある（実測では単一ブランチのfetchは約3.5秒）。
教訓: ブランチの内容を答える前に対象ブランチだけfetchする。手元の作業内容の話はローカル、それ以外は `origin/<branch>` を基準にし、乖離があれば差分を述べる。

## 長時間待機（CI・ビルド・OTA等）の作法 (2026-08-24)

**経緯**: usbguard block モードのCI（Push run 32724726324、arm-build 80分想定）を Monitor で監視した。Monitor のイベント条件を「ジョブ結果の状態変化のみ」にしたため、ジョブ完了までの十数分間ずっと無出力になった。ユーザーから「10分以上放置しないように。セッションが死ぬ」と指摘を受けた。

**根本原因**: 状態変化ベースのイベント設計は、変化がない間の出力が0になる。CIの各ジョブは数十分単位で進むため、無出力区間が容易に10分を超える。セッション維持に必要な最小出力頻度を設計に織り込んでいなかった。

**教訓**: 待機は「イベントが来たら報告する」ではなく「一定間隔で必ず何か出力する」設計にする。heartbeat を先に決めてから、その上にイベント通知を載せる。加えて長時間待機が確定している場合は、待ち時間を独立作業（適用手順の準備、後片付け対象の洗い出し）に充てる。
